# Bug 修复循环 Spec（v1.0 草案）

> 来源：2026-10-15 用户描述的三层 loop（poteto 流派：验证前置、约束进环境）。
> 状态：v1.0 正式版（2026-10-15，用户授权助手拍板三项待定事项后定稿）。

## 1. 目标与非目标

- 目标：Slack 反馈 → Linear 工单 → 复现 → 修复 → fuzz → 人工拍板 → 合并，全程自动化，人只在最后一步拍板。
- 非目标：需求开发、大重构、线上 P0 事故应急（事故走人工通道，不进 loop；P0 缓解后的根因修复可作为 P1 进 loop）。

## 2. 三层总览

```
外环（分诊）：Slack 反馈频道 → 去重 / 分级 / 分流 → Linear 工单
内环（执行）：复现（pstack）→ 修（PR）→ fuzz（一小群 agent）→ 不干净回修
闸门（人工）：fuzz 干净 + CI 绿 + review → Slack ping → 按风险等级审批 → rebase 合并 → 接下一条
```

## 3. Ticket Schema（Linear 工单固定字段）

| 字段 | 必填 | 说明 |
|---|---|---|
| title | 是 | `[模块] 一句话描述` |
| severity | 是 | P0（阻塞/数据错）/ P1（核心功能坏）/ P2（一般）/ P3（体验问题） |
| reporter | 是 | Slack 用户 + 原消息链接 |
| 环境上下文 | 是 | 版本号、OS、配置、pstack 抓的现场 |
| 复现步骤 | 是 | 编号列表，别人照着能走通 |
| 期望 vs 实际 | 是 | 一句话各写清 |
| repro 产物 | 复现成功后 | repro 脚本/用例链接（必须进 PR） |
| fuzz 报告 | fuzz 后 | 干净与否、迭代次数、crash 记录 |
| 状态 | 是 | 见状态机 |

状态机：`待分诊 → 待复现 → 复现中 → 待修复 → 修复中 → fuzz中 → 待审批 → 已合并`
分支状态：`needs-info`（可重入）、`已关闭`（重复 / 非 bug / 无法复现 / 需求转出）。

## 4. 外环 Spec（Slack → Linear）

执行者：Grok Bot（常驻监听）+ 幕僚长（分诊规则 owner）。

1. 触发：反馈频道出现新消息（thread 内追加视为同一条反馈，不重复建单）。
2. 去重：建单前按「模块 + 关键词」搜 Linear，已有未关闭的相似单则关联原单、不新建，并在 Slack thread 回复原单链接。
3. 分级：按 severity 定义打 P0–P3；吃不准的默认 P2，人工可在闸门阶段改。
4. 分流（不是每句话都是 bug）：
   - bug → 进内环；
   - 需求 / 建议 → 移入需求池，不进 loop，Slack 回复去向；
   - 提问 / 咨询 → 直接在 Slack 回复（或转人工），不建单。
5. 建单：按 §3 schema 填单，状态 `待复现`，Slack thread 回复工单链接。

失败处理：Slack 监听掉线 → 按稳定 Bot 第 6 步静默重试，连续 3 轮失败上报；Linear API 失败 → 工单先落本地队列，重试 3 次，仍失败上报。

## 5. 内环 Spec（复现 → 修 → fuzz）

执行者：Engineer Bot（复现+修+PR）+ QA bot（fuzz 验收）。

### 5.1 复现
- 输入：工单的环境上下文 + 复现步骤 + pstack 现场。
- Engineer Bot 在云端机上复现。复现成功 → 产出 repro 脚本/用例（必须随 PR 提交），状态 → `待修复`。
- 复现失败 → 打 `needs-info`，写明**缺什么信息**（缺一不可列清单），经 Slack 退回 reporter。reporter 补信息后工单自动重入 `待复现`（按重入时间排队）。
- needs-info 超 48 小时无人补 → 升级给人定夺（关单或继续等），不许静默烂掉。

### 5.2 修
- 开 PR，PR 必须包含：repro 用例、修复 diff、改动说明。
- CI 全绿是硬门槛，红灯不许进 fuzz。
- 修完自检一遍 diff 再提交 fuzz。

### 5.3 fuzz
- 一小群 agent 针对 PR 的改动面写 fuzz target（有现成 harness 的复用，没有的现写，写不出 → 升级给人）。
- 「干净」定义（硬标准）：
  - 至少 10 分钟或 1 万次执行，零 crash；
  - 相对 base 分支无新增失败（回归对比）；
  - diff 行覆盖 100%。
- 不干净 → 回 `修复中`，迭代计数 +1；达到最大 3 次仍不干净 → 升级给人，附历次 fuzz 失败记录。
- fuzz 只抓 crash，**抓不到逻辑修错**：diff 正确性必须另过一遍 review（reviewer agent；中/高风险单走人工看 diff，见 §6）。

## 6. 人工闸门 Spec

前置条件（缺一不可）：fuzz 干净 + CI 全绿 + review 通过。

1. Slack ping 他，附：PR 链接、改动摘要、风险等级、fuzz 报告、repro 用例。
2. 风险分级：
   - 低：测试、文档、注释、纯重构（无行为变更）；
   - 中：业务逻辑变更；
   - 高：鉴权、支付、数据迁移、生产配置。
3. 审批规则（2026-10-15 定稿）：
   - 低风险单：Slack ping 后 1 小时无异议 → rebase 自动合并。默认项为「执行」，但仅限低风险（定义见 §6.2，刻意收窄）。
   - 中/高风险单：必须显式批准；沿用现有纪律——10 分钟未回复=过期，不得执行，必须重新请求。默认项为「不执行」。
   - 定稿理由：三道机器门（fuzz 干净 + CI 绿 + review）已在前，人工闸门对低风险单只是 backstop；1 小时是给人真实的反应窗口，10 分钟对低风险单只会造成无限重请求。
4. 合并后：Linear 关单（状态 `已合并`），Slack 原 thread 回复已修复 + 版本号，按 §8 队列接下一条。

## 7. 失败处理与升级矩阵（稳定 Bot 第 6 步）

| 场景 | 自动重试 | 上限 | 超限后 |
|---|---|---|---|
| Slack 监听掉线 | 静默重试 | 连续 3 轮 | 上报 |
| Linear 建单失败 | 重试，本地队列暂存 | 3 次 | 上报 |
| 复现失败 | 不自动重试，走 needs-info 回路 | — | 48h 无人补 → 升级给人 |
| CI 红灯 | 修完重跑 | 随 §5.3 迭代计数 | 计入 3 次上限 |
| fuzz 不干净 | 回修重 fuzz | 3 次 | 升级给人（附失败记录） |
| 闸门超时（中/高风险） | 不重试 | — | 视为过期，不执行，重新请求 |
| 升级后 24h 无人处理 | — | — | 幕僚长再次上报 |

## 8. 队列纪律

- 优先级：P0 > P1 > P2 > P3；同级按工单创建时间 FIFO；needs-info 重入的按重入时间排。
- 一次只修一条，合并后接下一条，不并行开多条（避免 agent 打架）。

## 9. 可观测性（可审查，稳定 Bot 第 3 步）

- 每单留：依据（pstack 现场/Slack 链接）、中间产物（repro、PR、fuzz 报告）、状态流转、失败原因。
- 周指标：MTTR、needs-info 率、平均 fuzz 迭代次数、自动合并占比、升级率。

## 11. 决策记录

2026-10-15，用户授权助手拍板三项待定，定稿如下：

1. 门禁规则：采用风险分级。低风险单 1 小时无异议自动合并（默认项「执行」）；中/高风险必须显式批准，10 分钟未回复=过期不执行（默认项「不执行」，沿用现有纪律）。理由：机器三道门在前，低风险定义收窄，1 小时是真实反应窗口。
2. 阈值：needs-info 48h 超时升级；fuzz 至少 10 分钟或 1 万次执行零 crash；最大迭代 3 次；diff 行覆盖 100%。理由：48h 照顾 reporter 时区与周末；10 分钟是回归门槛不是安全审计（重型 fuzz 走 nightly）；3 次修不好大概率是设计问题，转人工更划算；bug fix 改动面小，100% diff 覆盖可达且有意义。
3. P0 事故不进 loop：同意。P0 要的是即时人工应急（止血、通告），loop 的延迟结构不适配；P0 缓解后的根因修复可作 P1 进 loop。
