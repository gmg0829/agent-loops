# 巡逻循环 Spec（v1.0）

> 来源：2026-10-15 用户确认的常驻巡检 loop 描述，对标 pstack `/loop` 思想。
> 状态：v1.0。cron 本体待建（需用户拍板排期）。

## 1. 目标与非目标

- 目标：高频 + 有记忆的巡逻，每 15 分钟扫一遍责任面，异常轻处置或升级，正常静默。
- 非目标：不替 specialist 干重活（不修 bug、不验收、不写代码）；不做重执行；不碰对外动作。

## 2. 形态

- 节拍：每 15 分钟一轮（cron）。
- 「常驻」的务实实现：密 cron + 状态文件（watermark）模拟常驻。VM 重置会杀进程，真常驻不可靠；巡逻的本质是「高频 + 有记忆」，不是进程不死。
- 每轮五步：读上次状态 → 扫责任面 → 对比变化 → 处置/上报 → 写回状态。

## 3. 责任面

| # | 责任面 | 检查项 | 阈值与动作 |
|---|---|---|---|
| 1 | 团队看板 BOARD.md | 阻塞超时的单 | 阻塞 > 24h → 升级 |
| | | needs-info 超时 | > 48h 无人补 → 升级定夺 |
| | | stale 单 | 状态 > 72h 未变 → 提醒 owner |
| 2 | loop 健康 | bug/dev loop 卡住的单 | 迭代超限未升级 → 升级 |
| 3 | cron 健康 | 连续失败 | 同一任务连续 2 轮失败 → 上报 |
| | | 关键产出缺失 | 晨报/精选/日报没出 → 上报 |
| 4 | 飞书 bot 存活 | responder 进程 + 事件流 | 进程不在 → 尝试拉起；token 403 持续 → 上报（不再试） |
| 5 | 情报源健康 | 博客/列表源连续失败 | 同一源连续 2 轮失败 → 上报并标记 |

## 4. 处置三档

- 自修：重启 responder、按各任务第 6 步规则重跑失败轮次 → 记日志，不打扰。
- 升级：修不了的，按 §5 上报。
- 记录：纯信息记日志，不上报。
- 无问题静默（沿用现有纪律）。

## 5. 升级与去重

| 场景 | 动作 |
|---|---|
| 看板阻塞 > 24h / needs-info > 48h | 升级给人 |
| cron 连续 2 轮失败 | 上报一次 |
| 飞书 bot 拉不起 | 上报一次，状态未变则静默 |
| 情报源连续失败 | 上报并标记源状态 |

去重纪律：同一问题未解决前每轮只报一次；状态变化（恶化/恢复）才再报。不用每轮骚扰。
