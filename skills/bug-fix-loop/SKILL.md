# Bug 修复循环

## Purpose
Slack 反馈驱动的全自动 bug 修复循环：分诊建单 → 复现 → 修 → fuzz → 人工闸门 → 合并。
当用户说"跑一遍修 bug 循环"、"这条反馈进 loop"或 Slack 反馈频道有新 bug 时，用本 skill。
完整版 spec（含决策记录）：`../specs/BUG_LOOP_SPEC.md`（v1.0）。

## 三层总览
```
外环（分诊）：Slack 反馈 → 去重 / 分级 / 分流 → Linear 工单
内环（执行）：复现（pstack）→ 修（PR）→ fuzz（一小群 agent）→ 不干净回修
闸门（人工）：fuzz 干净 + CI 绿 + review → Slack ping → 按风险审批 → rebase 合并 → 接下一条
```
P0 事故不进 loop（走人工应急）；P0 缓解后的根因修复可作 P1 进来。

## 外环：分诊建单
1. 触发：反馈频道新消息（thread 追加视为同一条，不重复建单）。
2. 去重：按「模块 + 关键词」搜 Linear，已有未关闭相似单则关联原单，Slack thread 回原单链接。
3. 分级：P0 阻塞/数据错 / P1 核心功能坏 / P2 一般 / P3 体验问题；吃不准默认 P2。
4. 分流：bug → 内环；需求/建议 → 需求池（Slack 回去向）；提问 → Slack 直接回，不建单。
5. 建单字段：title`[模块] 一句话`、severity、reporter+原消息链接、环境上下文（版本/OS/配置/pstack 现场）、复现步骤、期望 vs 实际。状态 `待复现`，Slack thread 回工单链接。
6. 失败：Slack 监听掉线静默重试，连续 3 轮失败上报；Linear API 失败先落本地队列，重试 3 次仍失败上报。

## 内环：复现 → 修 → fuzz
### 复现
- 云端机上用 pstack + 工单环境上下文复现。成功 → 产出 repro 脚本/用例（必须随 PR 提交），状态 → `待修复`。
- 失败 → 打 `needs-info`，列清缺什么信息，经 Slack 退回 reporter；补信息后自动重入 `待复现`。48h 无人补 → 升级给人定夺，不许静默烂掉。

### 修
- 开 PR，必须含：repro 用例、修复 diff、改动说明。CI 全绿是硬门槛，红灯不进 fuzz。

### fuzz
- 针对 PR 改动面写 fuzz target（有 harness 复用，没有现写，写不出 → 升级）。
- 「干净」= 至少 10 分钟或 1 万次执行零 crash + 相对 base 无新增失败 + diff 行覆盖 100%。
- 不干净 → 回修，迭代计数 +1；3 次仍不干净 → 升级给人，附历次失败记录。
- fuzz 只抓 crash：diff 正确性另过 review（中/高风险走人工看 diff）。

## 人工闸门（v1.0 定稿规则）
前置：fuzz 干净 + CI 绿 + review 通过，缺一不可。
1. Slack ping：附 PR 链接、改动摘要、风险等级、fuzz 报告、repro 用例。
2. 风险分级——低：测试/文档/注释/无行为变更的重构；中：业务逻辑变更；高：鉴权/支付/数据迁移/生产配置。
3. 低风险单：1 小时无异议 → rebase 自动合并。中/高风险：必须显式批准，10 分钟未回复=过期，不得执行，重新请求。
4. 合并后：Linear 关单，Slack 原 thread 回已修复+版本号，按队列接下一条。

## 失败升级矩阵
| 场景 | 处理 |
|---|---|
| Slack 监听掉线 | 静默重试，连续 3 轮失败上报 |
| 复现失败 | needs-info 回路；48h 无人补 → 升级 |
| fuzz 不干净 | 回修重跑，上限 3 次 → 升级（附记录） |
| 闸门超时（中/高风险） | 视为过期，不执行，重新请求 |
| 升级后 24h 无人处理 | 再次上报 |

## 队列纪律
一次一条，P0 > P1 > P2 > P3，同级按创建时间 FIFO；needs-info 重入按重入时间排。不并行开多条。

## 可观测性
每单留：依据、中间产物、状态流转、失败原因。周指标：MTTR、needs-info 率、平均 fuzz 迭代、自动合并占比、升级率。
